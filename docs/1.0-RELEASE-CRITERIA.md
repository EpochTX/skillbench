# SkillBench 1.0 Release Criteria

SkillBench 1.0 is a compatibility and reliability promise, not only a version-number change. The project should not publish `1.0.0` until every blocking criterion below is satisfied by the exact release candidate tree.

## 1. Deterministic rule quality

- Every built-in rule is represented by at least one labeled positive corpus case before 1.0.
- The maintained release corpus has 100% rule coverage.
- The release corpus meets 100% precision and 100% recall at the case × rule level: no unexpected rule IDs and no missing expected rule IDs.
- Defensive and negative examples are included for security-sensitive rules so common documentation examples do not silently become high-severity false positives.
- Changes to rule behavior update corpus labels intentionally in the same pull request; CI must never regenerate labels from current output.

The repository benchmark command is:

```bash
skillbench benchmark tests/corpus/rules.yml --ci
```

The maintained corpus currently contains six full-stack repository fixtures plus deterministic generated threshold fixtures. Its 17 labeled cases cover all 24 built-in rules and are gated at 100% precision, 100% recall, and 100% rule coverage. Generated fixture inputs are deterministic, but expected rule labels remain human-authored and are never derived from analyzer output.

## 2. Stable CLI contract

- All documented commands have end-to-end tests against the production `dist/cli.js` build.
- Exit codes are stable and documented: success, policy/CI failure, and usage/runtime error remain distinguishable.
- JSON output is not mixed with progress or human-only messages on stdout.
- `--output`, `--no-color`, Windows paths, Unicode paths, CRLF files, and paths containing spaces are covered where applicable.
- Breaking command or flag changes require an explicit migration note and a major version after 1.0.

## 3. Stable public TypeScript API

- The supported public exports are documented and protected by contract tests.
- Declaration generation succeeds on every release candidate.
- Public types do not expose accidental internal implementation details.
- After 1.0, removals or incompatible type changes require a major version; deprecations should precede removal when practical.

## 4. Safe fix guarantees

- `skillbench fix` remains read-only by default.
- Writes require explicit `--write` opt-in.
- Automatic fixers are deterministic, idempotent, narrowly scoped, and covered by positive and negative tests.
- Ambiguous structural changes and security-sensitive remediation remain review-only unless a future fixer can prove a deterministic safe transformation.
- Apply rejects stale plans and targets that changed type.
- Replacement content is staged before commit, requested backup destinations are preflighted, and per-file replacement uses same-directory rename semantics.
- Partial multi-file failures attempt rollback and preserve recovery material when rollback cannot complete.
- Line endings and relevant file permission bits are preserved.

## 5. Report and schema compatibility

- `schemaVersion` changes only when the machine-readable report contract changes.
- JSON, SARIF 2.1.0, and GitHub annotation reporters have regression coverage for escaping, locations, metadata, and secret redaction.
- Stable issue fingerprints are independent of source-line movement and configuration-only severity overrides.
- Compare/diff remains severity-sensitive so a warning-to-error escalation is still visible as a regression.
- Any incompatible report-schema change has a migration note and an intentional schema-version bump.

## 6. Cross-platform support

The exact release candidate must pass the supported matrix without `continue-on-error`:

- Node.js 20 on Ubuntu
- Node.js 22 on Ubuntu
- current GitHub-hosted macOS runner
- current GitHub-hosted Windows runner

Each supported environment must run the relevant tests, production build, and built-CLI smoke tests. Node.js 20 support must not be silently lost through runtime dependency upgrades.

## 7. Package and supply-chain readiness

- `pnpm install --frozen-lockfile` succeeds from a clean checkout.
- `pnpm release:check` succeeds on the release candidate.
- `pnpm pack --dry-run --json` contains only intended runtime code, documentation, license, and referenced assets.
- The packed CLI is tested before publication.
- GitHub Actions references remain pinned to immutable full commit SHAs.
- Workflow permissions remain least-privilege for their task.
- Dependency lifecycle scripts stay explicitly allowlisted.
- Production dependencies have no unresolved known high/critical security issue accepted without a documented rationale.
- npm publication uses trusted publishing/OIDC and provenance when the npm package configuration is ready; long-lived npm tokens must not be committed or embedded in workflows.

## 8. Documentation and onboarding

- Chinese and English READMEs describe the same supported commands and safety boundaries.
- Installation instructions are tested from a clean environment.
- npm/npx instructions and npm badges are added only after the package is publicly resolvable.
- `CONTRIBUTING.md`, `SECURITY.md`, and `RELEASING.md` match the actual workflow.
- At least one copy-paste CI example is validated against the released version.

## 9. Performance and scale

- A deterministic large-instruction/repository benchmark exists before 1.0.
- The release candidate has documented baseline runtime and memory measurements for that benchmark.
- Performance regressions large enough to affect normal CI usage are investigated before release rather than hidden by raising limits.

## 10. Release execution

Before creating `v1.0.0`:

1. Freeze the release candidate and stop unrelated dependency or refactor merges.
2. Confirm the full labeled corpus still meets 100% built-in-rule coverage, precision, and recall.
3. Run the full cross-platform CI matrix on the exact candidate.
4. Run `pnpm release:check` and inspect the package manifest/tarball.
5. Verify npm trusted-publisher configuration and package ownership externally.
6. Publish the package and verify the installed CLI in a clean environment.
7. Create the matching `v1.0.0` Git tag and GitHub release from the exact published commit.
8. Verify provenance, release links, badges, installation commands, and the `main` CI state.

A release is not considered complete merely because a tag exists or CI is green. The published npm package, GitHub release, documentation, and tested source tree must all identify the same version and commit.
